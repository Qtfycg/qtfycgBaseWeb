## 2. 产品概述

selectHelp 是一款帮助用户决定每餐吃什么的微信小程序。用户打开小程序后无需先填写问卷，系统根据当前场景直接给出 3 个候选。候选可以是“自己做”，也可以是“点外卖”，两类数量不固定，由匹配度动态决定。

产品希望把一次常见的用餐决策控制在 1～2 分钟内，同时兼顾轻松有趣的抽选体验、可靠的信息展示和逐步改善的个性化推荐。

### 2.1 核心价值

- 先给结果，减少开始决策前的填写负担。
- 同时比较自己做和点外卖，避免用户先决定用餐方式。
- 利用家中现有及临期食材，减少浪费。
- 结合附近商家，为外卖场景提供具体可执行的选择。
- 通过历史选择和餐后评价逐渐贴近个人口味。

### 2.2 目标用户

第一版主要服务产品所有者个人，并按可扩展为普通用户产品的标准设计。后续可以扩展多人共同决策，但第一版不定义具体多人玩法。

### 2.3 核心成功标准

- 用户无需填写初始问卷即可获得推荐。
- 用户通常能在 1～2 分钟内决定本餐选择。
- 推荐结果能解释“为什么适合现在”。
- 用户不满意时可以补充条件，而不是重新开始完整流程。
- 外部数据不可用时，自做推荐仍然可用。

## 3. 产品原则

1. **先结果，后条件**：打开即推荐，不用启动问卷。
2. **可靠胜过完整**：没有可信来源的数据不展示猜测值。
3. **有趣但不盲目**：随机只发生在高匹配候选之间。
4. **个人数据本地优先**：个人偏好、食材和历史第一版主要保存在本机。
5. **外部能力可替换**：位置、天气和外卖数据通过独立适配层接入。
6. **异常可降级**：单个接口失败不能让整条推荐链路不可用。

## 4. 版本范围

### 4.1 第一版范围

#### 推荐决策

- 打开小程序后直接生成 3 个候选。
- 候选池同时包含自做菜品和外卖选项。
- 根据匹配度动态决定两类候选数量。
- 支持补充预算、可用时间、口味和距离等条件后重新推荐。
- 展示候选的关键推荐理由。
- 记录最终选择和餐后评价。

#### 自己做

- 内置开发者维护的公共菜品库。
- 展示所需食材、用量、烹饪步骤和预计耗时。
- 管理家中食材的名称、数量、单位和保质期。
- 优先推荐能够使用临期食材的菜品。
- 计算缺少食材并生成采购清单。

#### 点外卖

- 在深圳全市范围搜索当前位置附近的餐饮商家。
- 在数据来源允许时展示具体菜品。
- 展示可获得的商家名称、菜品、预计价格、配送费、距离、预计送达时间、评分、销量和营业状态。
- 记录外卖选择及预计花费。
- 没有可靠实时数据时隐藏字段或明确显示“暂无实时数据”。

#### 个性化与统计

- 自动记录最终选择。
- 支持“喜欢 / 一般 / 不喜欢”餐后评价。
- 根据评价调整后续推荐权重。
- 近期已选择项短期降权，减少连续重复。
- 展示用餐历史、自己做与外卖次数、预计外卖花费等统计。
- 支持清除个性化学习结果。

#### 身份、投稿与审核

- 使用微信静默登录，不要求头像、昵称或手机号。
- 个人偏好、食材和历史仍以本地保存为主。
- 所有普通用户均可提交纯文字菜谱。
- 用户可以查看自己的投稿和审核状态。
- 管理员在小程序内审核投稿。
- 投稿审核通过后进入公共菜谱库。

### 4.2 第二版候选范围

- 拍照或扫描识别家中食材。
- 外卖跨平台价格比较。
- 跳转对应外卖平台下单。
- 云端同步个人偏好、食材、历史和评价。
- 多人共同决定吃什么，具体交互另行设计。

### 4.3 第一版明确不做

- 好友、群组、饭局和多人投票。
- 用户上传菜谱图片。
- 自动购买缺少的食材。
- 自建外卖交易、订单和支付。
- 未获授权的数据抓取。
- 大模型生成菜谱或推荐结果。
- 对深圳每一家餐厅的完整收录承诺。

## 5. 核心用户场景

### 5.1 午餐快速决策

用户午餐时间打开小程序。系统结合位置、午餐时段、默认预算、可接受时间、天气和近期历史，展示 3 个候选。用户查看后直接选择其中一个，整个过程不超过 1～2 分钟。

### 5.2 利用临期食材做饭

用户家中有即将到期的番茄和牛肉。系统提高相关菜谱权重，解释“现有食材覆盖 80%，番茄明天到期”。用户选择菜谱后查看步骤，并将缺少食材加入采购清单。

### 5.3 首批候选不满意

用户对初始候选不满意，打开条件面板，设置“30 元以内、30 分钟内、不要太辣”。系统保留其他上下文并重新生成 3 个候选。

### 5.4 外卖接口不可用

天气或外卖数据服务失败时，系统明确提示部分实时信息暂不可用，并继续用本地菜品、食材和历史生成自做候选。

### 5.5 用户投稿菜谱

用户填写菜名、简介、口味、餐次、耗时、食材、用量和步骤，提交后进入“待审核”。管理员通过仅管理员可见的页面审核；通过后进入公共菜谱库，拒绝时必须填写原因。

## 7. 核心流程

### 7.1 首次打开

1. 小程序执行微信静默登录。
2. 请求定位授权，并获取当前时间。
3. 成功定位后获取深圳附近商家和天气。
4. 读取本地默认预算、可用时间、口味、食材和历史。
5. 生成并展示 3 个候选。

如果用户拒绝定位，系统允许手动选择深圳行政区或输入地点。拒绝定位不影响自做推荐。

### 7.2 初始推荐

1. 用户进入“吃什么”首页。
2. 页面直接展示 3 个动态候选。
3. 每个候选展示类型、名称、核心信息和至少一条推荐理由。
4. 用户选择候选，或打开条件面板调整后重新推荐。

### 7.3 选择自己做

1. 用户查看食材覆盖率、预计耗时和推荐理由。
2. 用户进入菜谱详情，查看食材、用量和步骤。
3. 系统对比家庭库存，生成缺少食材清单。
4. 用户确认本餐选择。
5. 系统记录历史，并在适当时间请求餐后评价。

### 7.4 选择点外卖

1. 用户查看商家、菜品、价格、距离、评分、营业状态和预计送达信息。
2. 页面按实际可获得的数据展示字段。
3. 用户确认本餐选择。
4. 系统记录历史和预计花费。
5. 第一版不在小程序内创建订单，也不承诺直接跳转平台。

### 7.5 餐后反馈

用户对本餐选择“喜欢 / 一般 / 不喜欢”：

- 喜欢：提升相似菜系、口味、菜品或商家的推荐权重。
- 一般：记录结果，不进行明显权重调整。
- 不喜欢：降低相似候选权重，但不永久屏蔽。

## 9. 推荐算法设计

第一版使用“规则评分 + 加权随机”，不依赖大模型。

### 9.1 候选生成步骤

1. 汇总餐次、位置、天气、预算、可用时间、口味、库存、保质期和历史。
2. 排除明确不可用候选。
3. 分别计算自做菜品和外卖候选得分。
4. 将两类结果归一化后进入同一候选池。
5. 对候选进行相似项去重。
6. 从高分候选中加权随机抽取 3 个。
7. 生成用户可理解的推荐理由。

### 9.2 评分因素

- 餐次匹配
- 预算匹配
- 制作或送达时间
- 口味匹配
- 家中食材覆盖率
- 临期食材利用程度
- 天气适配
- 商家距离和营业状态
- 近期重复程度
- 历史评价

各权重应支持配置。第一版通过测试数据和实际使用反馈调整，不在客户端代码中分散硬编码。

### 9.3 排除和降权

- 商家明确打烊：排除。
- 超出用户明确设置的最大距离：排除。
- 已过期食材：不计入可用库存。
- 近期已吃过：降权，不永久排除。
- 不喜欢的相似候选：降权，不永久排除。
- 外卖字段缺失：仅影响对应评分维度，不伪造默认值。

### 9.4 推荐解释

推荐理由来自实际参与评分的因素，例如：

- “家里的番茄明天到期，现有食材已覆盖 80%。”
- “距离 1.2 公里，当前仍在营业。”
- “符合你的微辣偏好，近 7 天没有吃过。”

系统不得展示没有数据依据的推荐理由。

## 10. 数据设计

- 默认预算与本次条件
- 口味偏好
- 家中食材和保质期
- 用餐历史
- 餐后评价
- 推荐学习权重

### 10.2 云端数据

- 匿名用户标识
- 公共菜谱
- 用户投稿
- 审核记录
- 管理员角色
- 外部服务调用所需的必要缓存
- 不包含密钥明文的配置记录

## 11. 技术架构边界

### 11.1 小程序端

- 沿用原生 TypeScript 微信小程序。
- 负责页面展示、本地数据、推荐交互和离线降级。
- 不保存外部服务密钥。

### 11.2 云端服务

- 处理微信静默登录和匿名身份。
- 提供公共菜谱、投稿和审核接口。
- 校验管理员权限。
- 代理位置、天气和外卖数据请求。
- 统一处理外部服务限流、超时和缓存。

### 11.3 外部服务

- 腾讯位置服务或等价服务：定位、区域解析、附近商家搜索。
- 合规天气服务：当前天气。
- 获得授权的外卖数据服务：商家菜单、价格、配送费和预计送达时间。

外部服务必须通过统一适配接口接入，使后续更换服务商不影响推荐和页面模块。

## 12. 外卖数据方案与风险

### 12.1 已选择方案

采用“分阶段接入真实数据”：

1. 第一阶段使用位置服务实现深圳全市附近餐饮商家搜索。
2. 同时申请外卖平台或合规数据服务的正式合作能力。
3. 菜品、价格、配送费和送达时间按真实获权字段逐步开放。
4. 第二版再实现跨平台比较与下单跳转。

### 12.2 公开能力判断

截至文档日期，可确认腾讯位置服务提供定位、搜索等 LBS 能力。美团存在生态开放平台和企业用餐合作能力；饿了么公开的蜂鸟平台主要面向商户、开发者和即时配送接入。由这些公开页面不能推导出普通小程序可以无条件获取深圳全市消费者外卖菜单与实时价格，因此外卖菜单属于正式合作依赖，不作为未经验证即可实现的基础能力。

参考：

- [腾讯位置服务](https://cloud.tencent.cn/solution/lbs)
- [美团生态开放平台](https://openapi.meituan.com/)
- [美团企业用餐开放平台](https://eps.meituan.com/open/)
- [美团企业版外卖 API 文档](https://h5.dianping.com/app/bep-docs/sky-doc/canyinopenapi/waimai_api.html)
- [蜂鸟即配开放平台](https://open.ele.me/register)

### 12.3 主要风险及应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 无法获得全城菜单权限 | 外卖候选无法稳定展示具体菜品 | 商家搜索先上线；具体菜品只在获得可靠数据后开放。 |
| 接口费用或合作门槛不确定 | 成本与发布时间不可控 | 数据适配层可替换；发布计划不绑定单一平台。 |
| 价格和配送数据快速变化 | 用户看到过期信息 | 展示来源与更新时间；过期字段隐藏，不作为实时承诺。 |
| 深圳全城数据质量不一致 | 不同区域体验差异 | 按深圳各区域抽样验收，记录空结果率和字段完整率。 |
| 外部接口超时或限流 | 推荐等待过久 | 设置短超时、缓存非实时字段、优先展示自做结果。 |
| 未授权抓取导致合规风险 | 上架受阻或产生法律风险 | 仅使用正式授权接口，不实施页面抓取。 |

## 13. 权限、隐私与安全

- 静默登录不得要求与核心功能无关的个人资料。
- 定位必须说明用途，并在拒绝后提供手动选择地点能力。
- 个人偏好、食材和历史第一版主要保存在本地。
- 用户可以清除本地历史和推荐学习数据。
- 云端仅存储投稿、审核和服务运行所需数据。
- 外部接口密钥只能保存在云端安全配置中。
- 管理员身份必须服务端校验。
- 投稿内容应进行长度、格式和敏感内容校验。
- 管理员操作应保留审核人、审核时间和结果记录。
- 上线前需配置微信小程序隐私保护指引，准确列出定位等数据用途。

## 14. 异常与降级

| 场景 | 处理方式 |
| --- | --- |
| 用户拒绝定位 | 允许选择深圳行政区或输入地点；继续提供自做推荐。 |
| 天气服务失败 | 忽略天气评分，不阻断推荐。 |
| 商家搜索失败 | 提示外卖数据暂不可用，优先提供自做候选。 |
| 菜单或价格缺失 | 隐藏对应字段或显示“暂无实时数据”。 |
| 候选不足 3 个 | 展示实际数量，说明限制条件，并提供放宽入口。 |
| 网络断开 | 使用本地菜品、库存和历史继续推荐自做候选。 |
| 投稿失败 | 保存本地草稿，支持稍后重试。 |
| 本地数据异常 | 恢复基础默认值，向用户说明需要重新填写的数据。 |
| 管理员权限失效 | 拒绝审核操作并重新校验身份。 |

## 15. 非功能需求

### 15.1 性能

- 正常网络下，推荐首页目标在 3 秒左右出现可用候选。
- 外部数据较慢时先展示已有结果和加载状态，不无限等待。
- 推荐、库存和采购清单计算不应造成明显页面卡顿。

### 15.2 可用性

- 核心流程在常见微信设备尺寸上正确显示。
- 主要操作应有明确加载、成功、失败和空状态。
- 趣味动效可跳过，不阻碍快速查看。
- 关键状态不能只通过颜色区分。

### 15.3 可维护性

- 推荐规则和权重集中配置。
- 外部数据服务使用统一接口。
- 页面、推荐、库存、投稿和审核职责分离。
- 外部字段缺失时页面可以安全渲染。

### 15.4 数据质量

- 外部动态数据包含来源和更新时间。
- 过期数据不按实时数据展示。
- 菜谱的食材单位应使用受控列表，避免采购清单无法计算。

## 16. 验收标准

### 16.1 核心推荐

- 打开小程序后不填写问卷即可看到推荐。
- 默认生成 3 个候选，或明确解释不足 3 个的原因。
- 候选动态混合自做和外卖。
- 每个候选至少有一条有依据的推荐理由。
- 同一批不存在明显重复候选。
- 用户可以调整条件并获得新结果。

### 16.2 自做与食材

- 食材可记录数量、单位和保质期。
- 临期食材能够影响排序。
- 已过期食材不计入库存。
- 菜谱展示完整食材、用量和步骤。
- 采购清单能够正确计算缺少数量。

### 16.3 外卖

- 在深圳各区域的抽样位置能够执行附近商家搜索。
- 商家字段缺失不会导致页面异常。
- 菜品、价格和配送数据只在有可靠来源时展示。
- 外卖接口失败时仍能完成自做推荐。
- 预计花费与真实支付金额在文案上明确区分。

### 16.4 个性化

- 最终选择进入历史记录。
- 三档评价能够影响后续权重。
- 近期选择会被降权。
- 用户可以清除历史和学习结果。

### 16.5 投稿与审核

- 普通用户可以提交文字菜谱并查看状态。
- 投稿失败后草稿仍然存在。
- 普通用户无法查看他人投稿。
- 非管理员无法调用审核操作。
- 拒绝必须填写原因。
- 通过后的菜谱可以进入公共菜谱库。

## 17. 测试重点

### 17.1 单元测试

- 推荐评分与归一化
- 加权随机的候选范围
- 相似候选去重
- 临期和过期日期边界
- 库存扣减与采购数量计算
- 餐次时间边界
- 评价对权重的影响

### 17.2 集成测试

- 静默登录和匿名身份
- 位置、天气和商家接口
- 外部字段缺失、超时、限流和空结果
- 投稿、审核和公共菜谱发布
- 管理员服务端权限

### 17.3 端到端测试

- 打开应用到确认自做候选
- 打开应用到确认外卖候选
- 初始不满意后修改条件
- 菜谱到采购清单
- 餐后评价到后续推荐变化
- 用户投稿到管理员审核
- 拒绝定位和网络中断的降级流程

### 17.4 城市覆盖抽样

- 在深圳各区域选择代表性住宅、办公和商业地点。
- 验证附近商家搜索是否返回合理结果。
- 记录空结果率、响应时间和字段完整率。
- 对数据缺口按服务商、区域和字段分类，不使用虚构数据补齐。

## 18. 产品数据指标

第一版至少记录以下不含敏感内容的产品事件：

- 推荐成功或失败
- 初始候选数量
- 用户是否修改条件
- 从打开到确认选择的时长
- 最终选择为自做或外卖
- 用户评价结果
- 外部接口是否降级
- 投稿、通过和拒绝数量

重点观察：

- 1～2 分钟内完成决策的比例
- 首批 3 个候选直接被选择的比例
- 平均调整条件次数
- 近期重复率
- 外卖数据完整率
- 推荐后获得“喜欢”的比例

## 19. 发布条件

第一版发布前必须满足：

1. 核心推荐、自做、食材和采购清单流程完成。
2. 深圳附近商家搜索通过区域抽样。
3. 外卖字段仅展示已获授权且验证可靠的数据。
4. 投稿和管理员审核权限通过安全测试。
5. 定位拒绝、外部接口失败和断网降级可用。
6. 微信小程序隐私保护配置与实际数据处理一致。
7. 核心端到端流程在目标设备上通过。

外卖具体菜单、实时价格和配送信息若尚未获得正式数据能力，不阻止自做与商家搜索版本验证，但页面必须明确能力边界，不能将缺失信息包装成实时结果。
